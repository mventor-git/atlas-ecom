## Implemented

- TypeScript registry for `core -> cluster -> plugin -> module`, with the local commerce hierarchy and the catalog, orders, presentation, cart, checkout, and payment capability seeds. The durable-checkout slice added the first third-party runtime dependency, `pg` (^8.23.0), used only by the durable order store; the tokenization added none, and every other path still runs on the standard library.
- Process-local Atlas Connect kernel covering major-version handshake, malformed-manifest rejection, share-only pairing, explicit `master`/`reader`/`proposer` authority, snapshots with opaque cursors, ordered deltas, idempotent inbox handling, and proposal transitions.
- `npm run smoke` standalone registry entry point. The protocol adapter is deliberately volatile test infrastructure, not production persistence.
- In-memory `StandaloneCatalog` for local product add/update/deactivate/list and `Cart` for active-product lines, availability checks, integer-cent totals, and first-added line order. Both operate without a peer.
- `Cart.checkout()` revalidates active products, current prices, and availability; rejects empty, stale-price, inactive, insufficient-stock, and duplicate-line inputs before mutation; atomically decrements catalog quantities; clears the cart; and returns an immutable `Order` with `status: "created"` and frozen line/total snapshots. This local checkout path is unchanged and its returned order is still not persisted.
- `OrderBook` records successful checkouts in memory and exposes `getOrder`, `listOrders`, and `summary`; it returns frozen order copies, omits unknown IDs, and does not take ownership of ERP data. `Order` gained three optional fields for peer-backed orders: `status` also accepts `"submitted"`, plus `source: "connected"` and the peer's own `remote_sale_id` so the two records can be reconciled without either side owning the other's data.
- `OrderBook.recordConnectedOrder` is the single controlled write path for a peer-backed order. It rejects anything that is not a `submitted` `connected` order, requires a non-empty `remote_sale_id`, and refuses to replace an id that is already recorded, so an order cannot be rewritten by a second attempt.
- `AtlasErpClient` is a minimal real HTTP client for the ERP loopback profile: health is read without authentication, manifest, audit, and sale-post reads/writes use the configured bearer token, requests are bounded, and response shapes are validated without leaking the token in errors. The audit payload is fully typed (`ErpAuditItem`, `ErpStockLevel`, `ErpSale`, `ErpJournalEntry`, `ErpStockMovement`, `ErpAuditData`, `ErpAuditSnapshot`), including the ERP item master.
- `ErpAuditConsumer` is the read side of the audit capability. It pins the peer `app_id`/`capability` and rejects an identity change, keeps only the last applied opaque cursor so re-reading the same position is a no-op, and exposes `listItems`, `listStock`, and `getStockLevel`. It projects ERP records; it does not adopt or own them. State is process-local, so a restart re-reads from the peer rather than resurrecting stale data, and there is no delta chain to walk in this snapshot-only profile.
- `ConnectedCatalog` is a read-only storefront projection joining ERP items to current stock into `ConnectedCatalogEntry` (`item_id`, `sku`, `name`, `price_cents`, `quantity`), with `list`, `getById`, and `getBySku`. An item with no stock record joins as quantity 0, which reads as unavailable. It holds no `StandaloneCatalog` and exposes no write path.
- `src/postgres-order-store.ts` is Ecom's durable record of a submitted connected order command. One `OrderCommandStore` interface declares `ensureSchema` / `reserve` / `complete` / `abort` / `close`, with two adapters: `InMemoryOrderCommandStore` for tests and standalone use, and `PostgresOrderCommandStore` for durability. The durable adapter owns exactly one Ecom table, `connected_orders` (`order_id` primary key, `request_hash`, a `status` check limited to `pending`/`completed`, a `response` jsonb receipt, `created_at`, `updated_at`). `request_hash` is the SHA-256 of the exact payload submitted, so the same key with a different payload is a conflict rather than a silent second order. `reserve` inserts with `ON CONFLICT DO NOTHING` inside one transaction so concurrent claims of one id resolve to exactly one winner. The table name is a constant, so no caller-supplied value reaches the SQL text.
- `ConnectedCheckout` is a real connected checkout rather than a smoke: one Ecom order, one peer submission, one durable receipt. It refuses to be constructed without `allowWrites: true`, resolves the item from `ConnectedCatalog`, rejects overselling and unsellable prices, reserves the caller's key, posts one single-line sale, verifies the peer's `total_cents` equals `unit_price_cents * quantity`, and only then completes the receipt. The peer's `sale_id` is derived from the key as `ecom-${key}`, so even a released claim that is retried cannot become a second peer sale. A failed peer call, or a peer total that does not match, aborts the receipt so the key can be retried; a failed abort is swallowed deliberately, because a claim left pending is the safe direction. A replayed receipt is re-validated field by field rather than trusted, so a hand-edited row fails loudly instead of handing back a malformed order, and recording is idempotent (`getOrder` before `recordConnectedOrder`) so a replay never replaces the first order.
- `connect:order-smoke` and `createManualSale` remain as the lower-level path: one typed manual-sale request and a guarded single-unit sale for the first in-stock item, still behind `ATLAS_ERP_ALLOW_WRITE=1`. They are a smoke, not a checkout, and they build no Ecom `Order`.
- `connect:checkout-smoke` is the real connected checkout against a real peer and a real database. It refuses to run without `ATLAS_ERP_ALLOW_WRITE=1`, reads its whole configuration before opening a peer connection or a database session, and never prints the connection string. It sells one unit, re-reads the peer audit and requires the cursor to advance and stock to fall by exactly the submitted quantity, then closes the order store, opens a new one, and repeats the same key: the replay must be answered from the stored receipt with the same order id and `sale_id`, must *not* move the peer's audit cursor, must leave stock unchanged, and must leave exactly one connected order in the `OrderBook`. Any of those failing is a non-zero exit.
- `db/` is a reproducible example dataset, not production persistence and not a migration set. `db/schema.sql` creates five tables in a dedicated `ecom_example` schema and `db/seed.sql` loads the shared catalogue: 6 categories, 6 products, 37 colour/size variants, exactly one image row per variant, and 37 stock rows. It lives in its own schema so it can sit beside real Ecom tables and be removed with one `DROP SCHEMA ecom_example CASCADE`. `products.product_id` deliberately holds the same value as the ERP item master `item_id`, and `variant_id` is the deterministic `<PRODUCT SKU>-<COLOR>-<SIZE>` composite, so this dataset and the `atlas-erp` example seed can be diffed or joined by id. Nothing in `src/` reads these tables: the only table the application owns is still `connected_orders`. Two seeded edge cases are deliberate: the two `Ember` bottle variants are `inactive`, and `SOL-TRAIL-BTL-EMBER-750ML` has 1 unit on hand so an oversell can be rejected.
- `src/demo-catalog.ts` is the UI's fixture: the `db/seed.sql` example catalogue as in-process data, copied verbatim where identity, price, stock, status, and imagery matter (6 products, 37 colour/size variants, one Unsplash image per variant, the two `Ember` bottle variants `inactive`, and `SOL-TRAIL-BTL-EMBER-750ML` on one unit so an oversell is a real case). Descriptions are abridged. `createDemoStore()` builds a real `StandaloneCatalog`, `Cart`, and `OrderBook` from it, so the pages drive the same domain the CLI smoke does rather than a parallel model, and `test/demo-catalog.test.ts` diffs the fixture against the committed seed so a seed change that is not mirrored here fails the suite. It reads no database.
- `src/commerce.ts` gained additive, optional display fields on `Product` (`brand`, `category`, `color`, `size`, `description`, `image_url`, `image_alt`) so a catalogue entry can carry what a page needs to render. Every field is optional, the frozen-record allowlist was extended to match, and no existing caller or test changed behaviour: this is additive, not a contract change, and the domain still ignores presentation data.
- `src/web-server.ts` is the first browser surface for both products, on `node:http` only, with no framework and no build step. `npm run web` serves the storefront at `127.0.0.1:4312` (override `ATLAS_ECOM_WEB_PORT`) and the operator `ecom-manager` at `/manager`. The storefront renders one card per product with real colour and size selects, integer-cent prices, variant images, an availability line, and a shared cart; checking out posts to the API and shows the resulting in-memory order. The manager renders the full variant stock table, the cart, the order summary, and an Add Product form, and states the demo limits on the page itself. All pages and every JSON response label the data `demo` / `in_memory`.
- The web API is `GET /api/health`, `GET /api/catalog`, `GET /api/cart`, `POST /api/cart`, `GET /api/orders`, and `POST /api/checkout`. Health and catalog report the counts a reader needs (`products`, `variants`, `sellable_variants`, `unavailable_variants`) plus `mode: "demo"`, `in_memory: true`, `database: "none"`, and `peer_connected: false`, so fixture state cannot be mistaken for a live system. A domain rejection on add-to-cart or checkout is the caller's fault and answers `400` with the domain's own message; an unknown route is `404` and a wrong method is `405`; a body over 8 KiB is `413` and is drained rather than buffered. `POST /api/checkout` returns `201` with `paid: false` and `persisted: false` on the payload, because it is neither.
- Both pages are tokenized against `contract.md` v1.1.1. The stylesheet declares the whole shared token table once per mode as `--atlas-*` custom properties under `:root, [data-theme="light"]` and `[data-theme="dark"]`, and every rule below those two blocks resolves to a variable, so no colour literal survives outside the token table. `<html>` carries `data-theme`, the mode is normalised to `light` or `dark` with a light fallback for an absent, empty, or unrecognised value, and `?theme=` is read on the page routes only: the JSON API is untouched by it, so a `?theme=` query can never change an API response. `themedPath` keeps the page's own parameters while setting the mode, so the theme link, the cross-page link to the other surface, the post-checkout redirect, and the manager's add-product redirect and error re-render all preserve the mode instead of resetting it, and a real order shown after checkout still renders in the chosen mode. Links keep an underline so they never rely on colour alone, `:focus-visible` draws its outline from the focus token, and the demo banner, out-of-stock, warning, success, and error states use the four `state.*` pairs. One rule carries the contrast finding rather than the palette: the contract derived `fg.muted` against `bg.canvas`, so it is a canvas colour, and `.card .meta`, `.card label` and `table .meta` repaint to `fg.default` on the surface, as do `dl.stats dt` and a disabled button. A state note is also a muted line inside a card, so the warning rule gained the compound `.meta.warn` selector to out-specify that repaint instead of losing its own pair to it. This added no dependency, no build step, and no framework: it is the same server-rendered CSS the slice already shipped.
- The web surface is a demo, and the limits are enforced rather than only documented. It binds loopback and takes no host argument in the CLI entry point, has no authentication, no accounts, no CSRF token, and no audit trail, and one shared cart serves every visitor. There is one process-local `DemoStore` per server, so stopping the process loses the cart, the orders, and anything the operator added. The store is built from the standalone branch of the contract: no peer is paired, so Add Product writes straight into the in-memory catalogue and the page says that a paired peer would make it a proposal instead. Money is integer cents throughout and never a float. Every dynamic value is HTML-escaped in one pass, the two inline storefront scripts are the only JavaScript on the page, and the operator surface is explicitly a standalone demo with no connection to Atlas ERP.
- `src/web-smoke.ts` (`npm run web:smoke`) is the one-shot check: it starts the server on an ephemeral port, reads every JSON route, fetches both pages, adds to the cart, checks out, reads the orders, and asserts an unknown route is `404`, then closes the server in a `finally`. No database and no peer are needed. The scripts `web` and `web:smoke` were added to `package.json` alongside the existing smokes, and `src/index.ts` re-exports `demo-catalog.ts` and `web-server.ts` so both are part of the package surface.
- `.gitignore` covers `node_modules/` (while keeping `package-lock.json`), `.env`/`.env.*`, local database and dump files, and logs. No ignore rule hides a tracked source file, and the web slice added no new ignore rule because it commits no generated asset: the pages are server-rendered at request time.

The gate is not met as written, and this file does not claim otherwise: every named token resolves on both pages in both modes and the muted-on-surface defect is closed, but two painted pairs are still short of AA, so what is demonstrated is the token layer only, and everything underneath both pages is still fixture and in-memory data. The contrast fix recorded the rest of it: the muted-on-surface defect is closed, and what the suite could not close is written down as `DOCUMENTED_SHORTFALLS` rather than papered over. The light `state.success` pair measures 3.38:1 and the contract itself calls it non-text and large-text only, yet `.ok-note` paints it as a .9rem status line after a checkout and after an add, so light mode is short of AA text there; the contract's own suggested repair is `#2D0000` on `#C7D3C0`, and no token in the table is that pair in both modes (`fg.default` is `#DFD8C8` in dark and `onAccent.default` is `#41444B`), so this is a contract decision, not a rule the stylesheet may take. Dark `border.control` on `bg.surface` is 2.79:1 for the same reason: the contract derived it against `bg.canvas`, where it is 3.73:1, and every control is painted on the surface. The one-line stylesheet answer is to fill controls with `bg.canvas` instead of `bg.surface`, which is what the ERP console does for its neutral chips; that was not applied here because the delegated scope for this slice named the text colours to change, so it is left for the parent to take or drop. The contrast assertions are computed from the token table rather than from a browser, so the cascade is pinned by selector text and the specificity claim in the comment above `.warn`   has not been re-checked by eye.
- The approved v1.2.0 frontends are not started, so acceptance gate 7 is not met. v1.2.0 fixes React 19 + TypeScript + Vite + Tailwind CSS v4 + shadcn/ui on Radix primitives as the direction for the storefront and the `ecom-manager`, and fixes the shadcn-to-Atlas variable mapping (`--background` to `bg.canvas`, `--foreground` to `fg.default`, `--card` to `bg.surface`, `--primary` to `accent.default`, `--primary-foreground` to `onAccent.default`, `--muted-foreground` to `fg.muted` on the canvas only, `--border` to `border.divider`, `--input` to `border.control`, `--ring` to `focus.ring`, and the state variables to the `state.*` pairs with `state.success.text` on the accessible ink and `state.success.indicator` as the non-text marker). None of that exists here: there is no Vite project, no React, Tailwind, or Radix dependency, no generated shadcn component, and no frontend source of any kind, and `package.json` still carries only `pg` plus the existing scripts. The mapping is specified, not built, so nothing about gate 7 is demonstrated, and the v1.1.1 token work on the two `node:http` pages does not count toward it. The existing pages stay as they are until a migration slice replaces them; the costs are recorded in the contract risks: a second and third Node build surface, a generated copy of every shadcn component the sibling ERP product also holds separately, and no check yet that both products' mappings still resolve to the same shared token values.
- `OrderBook` is still in memory. A connected order is durable only as a receipt row in `connected_orders`; after a restart the book is empty and the order reappears only when the same key is replayed through `ConnectedCheckout`. Nothing scans the table at startup to rebuild it, so `summary()` and `listOrders()` do not reflect prior orders until something replays them.
- The local commerce path is still entirely in memory. `StandaloneCatalog` products, `Cart` contents, and the order returned by `Cart.checkout()` are lost on restart. Only the connected order command is durable, so local and connected orders now have genuinely different durability and there is no single order store behind both.
- The dual-write window between Ecom and the peer is open. `reserve`, the peer `POST`, and `complete` are three separate operations with no transaction spanning them, so a crash after the peer accepted the sale but before the receipt was completed leaves a `pending` claim that reports "submission in progress" with no automated recovery. The derived `ecom-${key}` sale id is what keeps a manual recovery from becoming a second peer sale, but recovery itself is currently a manual `abort`. Closing this needs a lease or expiry plus an explicit reconcile step, added when a real crash is in scope.
- `PostgresOrderCommandStore` uses a single `pg` pool and no statement timeout, retry, or health check; a database outage surfaces as a rejected promise from the checkout. Operational database behaviour belongs with the real persistence work.
- The customer storefront and the `ecom-manager` UI exist now, as an in-memory demo only. Neither is a product surface: there is no authentication, no accounts or sessions, one shared cart for every visitor, no CSRF protection, no audit trail, no persistence, and no connection to a peer, and both pages say so. A submitted or checked-out order is still neither paid nor persisted, so payments, order persistence, and real customer accounts remain deferred along with them. The manager's Add Product is the standalone branch written straight into the in-memory catalogue, and it becomes a Connect proposal only once a peer actually holds the capability.
- Full HTTP pairing/transport, one-time-code and scoped-credential exchange, TLS, hardened authentication, production security, and real degradation/resynchronization. The current loopback exchange is a narrow profile.
- Connected business operations beyond the single connected order command, presentation consumption, connected Add Product proposals, catalog/order synchronization back into Ecom, authority/import behavior, and full Connect conformance.
- Cart limitations are deliberate and unchanged: it uses the catalog price at the last add, and product quantity is availability only until checkout. `ConnectedCatalog` is a separate read projection and does not feed `Cart`, so a connected checkout is not a cart checkout.
- The real Ecom persistence schema. `db/` is example data in its own `ecom_example` schema with no migration runner, no version table, and no down-migration, and no code reads it. The contract's Ecom tables still have to be built and the local catalog, cart, and orders pointed at them.
- The web UI renders a *second* view of stock. The storefront's availability is the `StandaloneCatalog` quantity in the demo fixture, and the manager's stock table is the same quantity, while the connected path reads stock from ERP through `ConnectedCatalog`. The UI does not consume the connected projection at all, so an operator looking at the manager is not looking at the peer's stock. That gap closes when the manager reads `ConnectedCatalog` and the fixture stops standing in for real data, not before.
- Licensing and attribution for the example imagery. The 37 image rows point at 13 shared `images.unsplash.com` CDN links as placeholders, no image files are committed, and this repository carries no photographer attribution. Linking a CDN URL is not the same as being licensed to sell the photograph, so before anything reaches a real storefront each photo needs the normal Unsplash licence review at the time of use, per-photographer attribution where the photographer has asked for it, the API terms if the links ever switch to the API, and a decision on hotlinking and caching versus downloading and self-hosting. The demo pages render those same links and carry the warning in their footers, which is a placeholder, not a review. That review is product work and has not been done.
